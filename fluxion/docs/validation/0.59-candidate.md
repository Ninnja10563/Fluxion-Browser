# Fluxion 0.59 Browser Memory privacy candidate

Status: implementation and local verification in progress; not published.

## Motivation and scope

The previous policy rejected `/account` but allowed `/%61ccount`, even though
servers can route both to the same sensitive page. Indexing and result filters
shared that raw-path check. Tightening only the filter would leave previously
extracted text and vectors in the enriched database.

The shared policy now conservatively decodes paths for classification only.
New evidence is checked at extraction boundaries and again at store insertion.
Existing enriched evidence is swept before the first connection is exposed,
including non-private startup with Memory disabled. Excluded native vectors
retain their established content-free sentinel treatment; ordinary Places
history is not deleted.

## Required evidence

- Encoded letters, separators, nested escapes and malformed-input policy tests.
- Shipped runtime extraction and all partial/final result-source filtering.
- Transactional enriched text/vector cleanup, safe-neighbor retention,
  startup failure isolation, bounded keyset batches and stale-work invalidation.
- Actual native vector-byte scrubbing and enriched SQLite cleanup on macOS.
- Two-launch legacy-profile verification with Memory disabled: startup alone
  deletes excluded evidence while retaining safe vector bytes and Places visits.
- Full release staging, including all existing browser gates and actual
  anonymous update discovery, before promoting the exact tested DMG.

## Limits

Sensitive-route detection remains heuristic. Category exclusions and broader
resource/platform-accessibility work remain unfinished. Logical database
deletion does not establish forensic erasure from media or backups. Synthetic
vectors test storage/privacy behavior, not model inference quality.
